What one request costs · Lesson 02

Where 200 milliseconds go

A user taps a button and, a fifth of a second later, a screen appears. Everything you will ever do about performance depends on knowing what happened in that fifth of a second — and the honest answer is that two hops took nearly all of it, and neither of them was your code.

01Ground floor

One tap, eight hops

TAPAny word with a dotted underline opens a plain explanation in English and Vietnamese, plus where that thing shows up once a system is actually running. Nothing here assumes you have met it before.

Follow one request from a phone in Hanoi to a server in Singapore and back. Before the server hears anything, the phone has to turn a name into an address — a — then open a connection with a TCP handshake, then agree on encryption keys with a . Each of those is a conversation, and a conversation with somebody 2,000 kilometres away takes at least one : out and back, about 30 milliseconds each, because light in fibre is fast but not free.

Only then does the actual request leave. It arrives at a , which spends half a millisecond choosing one of the application servers behind it. The server parses the request, checks who is asking, runs the business logic — a few milliseconds, on a normal day. It asks the database for a row: half a millisecond across the datacenter network, two milliseconds for an indexed lookup, half a millisecond back. The response is assembled and sent, and takes the same 30 milliseconds to reach the phone that the request took to leave it.

Add it up and the shape is unmistakable. The trip across the wide-area network shows up once on a warm connection and four times on a cold one. The database shows up once per query. Everything else — the load balancer, the application code, the datacenter hops — is loose change. Two kinds of hop carry the time, and both of them are round trips.

In productionThe browser's network panel draws exactly this as a waterfall: DNS, connect, TLS, waiting, download. Server logs start at "waiting" and end before "download". The two never agree on how long a request took, and the browser is the one telling the truth, because it is measuring from where the user sits.

Cộng lại thì hai loại chặng chiếm gần hết thời gian — chuyến đi-về qua mạng diện rộng và database — và cả hai đều là những vòng đi-về, không phải code của bạn.

02The idea

The unit of latency is the round trip, not the line of code

Light travels about 200 kilometres per millisecond in fibre, and a packet rarely takes the straight line. Hanoi to Singapore is a round trip of roughly 30 ms; to Frankfurt, 150 or more. That number is a property of geography. You can shrink it in exactly two ways — put the server closer to the user, or cross the gap fewer times — and neither of those is a faster algorithm.

That is why the count of round trips matters more than almost anything you do inside the server. A cold connection costs three extra conversations before the first byte of your request moves: DNS, TCP, TLS. On a connection kept open — — the second request pays for none of them. For a user on the far side of an ocean, that single configuration flag is worth 300 milliseconds, more than every optimisation you could make to the code combined.

The same arithmetic applies inside the datacenter, on a smaller scale. A round trip to the database is half a millisecond plus the query. That sounds like nothing, and it is nothing — once. A screen that lists forty orders and then fetches each order's customer with its own query makes forty-one trips, one after another. At 2.5 ms each, the database has just cost more than the ocean did. The database is not slow. It is being asked forty-one times when once would do. That pattern has a name, the , and it is the most common performance bug in existence because it is invisible in code that looks perfectly reasonable.

You cannot make light faster. You can only ask for fewer trips, or make them shorter.

So the budget for a 200 ms request, written honestly, looks like this. One trip across the wide-area network: 30 to 150 ms, depending on where the user is. One trip to the database: 2 to 3 ms if the query is indexed, 40 or more if it is not. Load balancer, application code, serialisation: 3 or 4 ms in total. On a cold connection, add three more wide-area trips at the top. Everything you will ever be asked to "make faster" is one of those lines, and the first job is to find out which.

There is one more number the average hides. Measure a thousand requests and most take 40 ms — but ten of them take 900. That is , and it comes from things that happen occasionally: a garbage-collection pause, a lock held a moment too long, a cache that had to be refilled, a retry. A user who loads a screen with ten requests on it meets the slow one about one time in ten. Design for the p99, not the mean, because the p99 is what a real person feels.

In productionConnection pools are keep-alive by another name: the HTTP client keeps a few sockets open to each host, the database driver keeps a few connections to the database, and the handshake happens once per pool rather than once per request. When the pool is missing or too small, the waterfall shows a handshake on every request and nobody can explain why the service is slow "even though the code is fast".

Tiếng ViệtĐơn vị của độ trễ là vòng đi-về, không phải dòng code. Khoảng cách địa lý không code nào rút ngắn được; chỉ có hai cách: đặt server gần hơn, hoặc đi qua khoảng cách đó ít lần hơn. Kết nối giữ mở (keep-alive) bỏ được ba vòng đi-về ở request thứ hai. Bên trong trung tâm dữ liệu cũng vậy: N+1 truy vấn biến database "nhanh" thành chặng chậm nhất. Và đo p99, không đo trung bình.

03The danger

Every hop lies about itself

Each component reports its own time, and each report is true. The application server says 3 ms. The database says 2 ms per query. The load balancer says half a millisecond. Add up what the components say and you get 6 ms; the user experienced 200. The missing 194 are in the gaps between the reports — the round trips — and no single component owns them. That is why performance work done from inside one component so often changes nothing the user can feel.

The chatty server

The code is clean: load the list, then for each item load its details. Each query is 2 ms, so the reasoning goes, and the database is "fine". The list has forty items today and four hundred next year, and the screen's load time grows in a straight line with it. Nobody wrote a slow query; somebody wrote forty-one fast ones, in sequence. The fix is not a faster database. It is one query with a join, or one query with all forty ids, or — if they genuinely must be separate — firing them together so the round trips overlap instead of stacking.

The cold path nobody measured

The load test ran from a machine in the same datacenter, with a client that reused its connection, and reported 8 ms. The first real user was on a phone on the far side of the world, on a connection that had to be built from nothing. Three handshakes, four wide-area round trips, 600 ms — and a support ticket saying the app is slow. The test was accurate. It just measured a different request from the one the user makes.

The average that hides the user

A dashboard shows a mean of 40 ms and everyone relaxes. The p99 is 900 ms and nobody looked. The slow one-in-a-hundred is not random noise; it is a specific thing happening — a pause, a lock, a cold cache, a retry — and it is happening to a real person every few seconds at any reasonable traffic. Averages are what components report. Percentiles are what users experience.

The line you never cross

Never optimise a hop you have not measured from the user's side.

Open the waterfall before opening the profiler. Find the two biggest bars, name the round trips behind them, and only then decide what to change. Shaving a millisecond off code that runs for three, while a request crosses an ocean four times, is work that feels productive and changes nothing. The two hops that carry the time are almost never the ones the code owns.

Where the hops show up

Four places, each showing a different slice of the same request. Only the first one shows all of it.

  • The browser's network waterfallDNS, connect, TLS, waiting, download — one bar each, measured from the user's chair. The only view that includes the wide-area round trips.
  • The server's access logStarts when the request arrives and stops when the response leaves. Everything before and after is invisible, which is most of it.
  • The database's slow-query logShows the 40 ms scan clearly, and says nothing about the forty fast queries that added up to more.
  • A distributed traceOne span per hop, nested, with the gaps drawn as gaps. The closest thing to seeing the whole request at once — lesson 22.

In productionThe commonest performance incident has this shape: a screen got slower over months, no single query is slow, no single component is loaded, and the fix is one query instead of N. Nobody is surprised at the end, and nobody could see it from inside any one box.

    07Take away

    Five questions worth asking

    1. "Where does the time actually go? Show me the waterfall."
      The first sentence in any performance conversation. It moves the discussion from opinions about code to bars on a chart, and the two biggest bars are usually not where anyone was looking.
    2. "How many round trips is that?"
      Ask it of a cold connection, of a screen load, of a service that calls another service. Round trips are the unit; a design that makes fewer of them beats one that makes each one faster.
    3. "Is that per request, or per row?"
      The question that finds N+1 before it ships. A 2 ms query is nothing once and a hundred milliseconds forty times, and the code that does it looks perfectly clean.
    4. "What's the p99, not the average?"
      Averages are what components report; percentiles are what a person feels. A mean of 40 ms with a p99 of 900 is a slow system with a flattering dashboard.
    5. "Which of these hops can we move closer, and which can we skip?"
      The only two levers that work on the wide-area network. Everything else is 3 ms of application code that was never the problem.
