What one request costs · Lesson 04

Make the server forget

The first real scaling move is not a bigger machine. It is making every machine interchangeable, so a request can land anywhere and be answered. The thing standing in the way is almost always one small habit: a server that remembers something only it knows.

01Ground floor

The second server breaks the login

TAPAny word with a dotted underline opens a plain explanation in English and Vietnamese, plus where that thing shows up once a system is actually running. Nothing here assumes you have met it before.

One server, and everything is simple. A user logs in, and the server writes a note to itself — this person is authenticated, here is who they are — and keeps it in memory. Every request that user makes comes back to the same server, finds the note, and is served. It works perfectly, right up to the day one server is not enough.

So you add a second server and put a in front to share the traffic. Now the user logs in — the load balancer sends that request to server A, which writes its note. The next request goes to server B, which has never heard of this user, and asks them to log in again. The request after that goes back to A, which knows them. The user is logged in and logged out at random, and nothing in the code is broken. The note is just in the wrong place: in the memory of one server, in a world that now has two.

That note has a name — the — and where it lives is the single decision this whole lesson is about. Keep it in one server's memory and you can never have a second server. Move it somewhere every server can reach, and something larger becomes true: any server can answer any request, which means you can add servers, lose servers, and replace servers without a single user noticing. That property is called being , and it is the foundation every later scaling technique is built on.

In productionThe session is not the only note a server is tempted to keep. An uploaded file held on local disk, a cart in memory, a rate-limit counter, a scheduled job's "have I run yet" flag — each is the same bug waiting for the second server. The test is one question asked of every piece of in-process state: if the next request lands on a different server, does this still work?

Tiếng ViệtMột server thì đơn giản: ghi chú "đã đăng nhập" vào bộ nhớ, mọi request quay lại đúng server đó. Thêm server thứ hai và đặt load balancer phía trước, request tiếp theo rơi sang server chưa biết người dùng — thế là đăng nhập rồi vẫn bị hỏi đăng nhập. Code không sai; ghi chú nằm nhầm chỗ. Ghi chú đó là session, và chuyển nó ra chỗ mọi server với tới được chính là stateless — nền của mọi kỹ thuật scale sau này.

02The idea

Four places to keep the note, in the order people try them

One — leave it in memory, and pin the user. The load balancer can be told to send every request from one user back to the same server: . The note is found because the user always returns to where it was written. This works, and it is a crutch. Load drifts uneven, because users are not evenly busy and nothing rebalances them. A server that dies takes its users' sessions with it. And a deploy — which restarts every server — empties every memory anyway. Sticky sessions are a fine bridge for a week. They are not where you stop.

Two — put it in a shared store. Move the note to a small fast database both servers read — Redis is the usual choice. Now the login is written once and found by whichever server gets the next request. Any server answers any request; the server is stateless. The cost is honest and worth saying: the store is now a thing that must not die, one more box to run and watch, and every request pays one to it. For most systems that is a trade worth making, and it is the standard answer.

Three — put it in the client. Instead of storing the note on the server, hand it to the user in a signed token — a JWT is the common form. The user sends it with every request; any server checks the signature and trusts the contents, with no store and no round trip. The catch is the sharp edge of the whole lesson: a token cannot be un-issued. Once signed, it is valid until it expires, so a "log out everywhere" or a "ban this user now" needs a deny-list the servers check — which is a small shared store again, arriving through the back door. Tokens trade a storage problem for a revocation problem.

A server that remembers something only it knows cannot be replaced. A server that forgets can be multiplied.

Once the session is out of the way, being stateless is what makes the rest of scaling possible. — adding servers rather than buying a bigger one — only works when servers are interchangeable, and interchangeable is exactly what stateless means. A bigger machine eventually does not exist; a tenth identical machine always does. Autoscaling can add a server for the evening peak and remove it at midnight, because no user's session was living on the one it removed. And a can replace servers one at a time with no downtime — but only if a restart loses nothing a request needs. If the session was in memory, that same rolling deploy is the event that logs every single user out, once per release.

The load balancer earns a closer look, because it is the one part that has to know something about the servers: which of them are alive. It asks each server every few seconds — a — and stops sending traffic to any that stop answering. That check is trickier than it looks, and it is the subject of the next section, because a check that lies in either direction is worse than no check at all.

In productionThe shared store for sessions is the most common first use of Redis in a system, and it usually arrives before Redis is used as a cache (lesson 11). The two jobs are different: a lost cache entry is recomputed, a lost session logs somebody out. Size and protect the session store for the second standard, not the first.

Tiếng ViệtBốn chỗ để session, theo thứ tự người ta hay thử: (1) sticky — ghim người dùng vào một server, chạy được nhưng là cái nạng; (2) kho dùng chung (Redis) — server nào cũng đọc được, đây là câu trả lời chuẩn, đổi lại một round trip và một hộp không được chết; (3) token có chữ ký ở client — không cần kho, nhưng không thu hồi được trước khi hết hạn, nên logout/ban lại cần deny-list. Stateless là điều kiện để scale ngang, autoscale và rolling deploy hoạt động.

03The danger

The state you forgot you were keeping

Nobody sets out to build a server that cannot be replaced. It happens one convenient line at a time — a value kept in memory because it was right there, on a day when there was only one server. Each one is invisible until the second server, the first crash, or the next deploy makes it visible, all at once, in production.

The file on local disk

A user uploads a photo; the server saves it to a folder and returns success. The next request — resize it, show it, attach it — lands on a different server, where the folder is empty. The upload "worked" and the file is gone. Local disk is per-server memory with a longer name. Anything a later request needs goes to shared storage the moment there is more than one server, and that is every real system.

The health check that says 200 while the house burns

A that answers "OK" as long as the process is running will keep a server in rotation long after it has lost its database and is failing every real request. Traffic keeps arriving; every request errors; the dashboard is green because the health endpoint never touched the database. The check has to test what the server actually needs to do its job, or it is measuring the wrong thing and lying about the answer.

The health check that takes everyone down together

Overcorrect, and the opposite trap is waiting. Make every server's health check fail whenever the shared database is briefly unreachable, and one database blip marks every server unhealthy at the same instant. The load balancer now has nothing to send traffic to and takes the whole system down — over a hiccup the servers could have ridden out. A health check should report whether this server is fit to work, not whether a shared dependency it does not own is having a bad second.

The line you never cross

Never keep anything in one server that a later request cannot find somewhere else.

Before you add the second server, walk every place the code holds state between requests — the session, an uploaded file, a cart, a counter, a cached computation, a "have I already done this" flag — and for each one answer: if the next request lands on a different server, does this still work? Whatever answers no is moved to a shared store or handed to the client, now, while there is still only one server and the bug is theoretical. After the second server it is an incident, and it arrives on the same day as three others.

Where the state hides

Five hiding places, in rough order of how often they are missed.

  • The session in memoryThe classic. Fixed by a shared store or a signed token — the whole of section 2.
  • An uploaded file on local diskWorks until the next request lands elsewhere. Goes to object storage; the server keeps only a URL.
  • A rate-limit or counter in memoryEach server counts its own share, so the real limit is silently multiplied by the number of servers. Belongs in the shared store — lesson 20.
  • A background job's "have I run?" flagEvery server thinks it is the one, so the nightly job runs N times. Needs a lease, not a local boolean — lesson 16.
  • An in-memory cache of a slow computationNot a correctness bug — each server just has its own copy and a lower hit rate. The one kind of local state that is usually fine, on purpose.

In productionThe tell that state is hiding is a bug that only appears under load or after a deploy and cannot be reproduced on one machine. "Works locally, fails in production" with an intermittent login or a missing file is almost always a note kept in a place the next request could not reach.

Tiếng ViệtKhông ai cố tình viết server không thay thế được — nó đến từng dòng tiện tay một. Ba cái bẫy: file lưu trên đĩa local (request sau rơi sang server khác là mất), health check nông (trả 200 trong khi đã mất database), và health check quá sâu (một cú chớp của database chung hạ toàn bộ server cùng lúc). Luật: trước khi thêm server thứ hai, với mỗi state giữa các request, hỏi "request sau rơi sang server khác có còn chạy không?".

04See it

Where the session lives, and what breaks

Add servers, then choose where the session lives, then throw an event at it: a burst of ordinary traffic, one server dying, or a rolling deploy that restarts them all. Watch the login survive or not, and watch the load spread evenly or pile onto one box.

Start where every system starts — one server, session in memory, nothing wrong. Add a second and the same choice that was invisible a moment ago decides whether your users stay logged in.

07Take away

Five questions worth asking

  1. "If the next request lands on a different server, does this still work?"
    The one question that finds hidden state. Ask it of the session, the uploaded file, the counter, the cached value — everything the code keeps between requests. Whatever answers no is the bug the second server will expose.
  2. "Where does the session live — memory, a store, or the token?"
    Three answers with three different failure modes. Memory cannot survive a second server; a store is a box that must not die; a token cannot be revoked before it expires. There is no free option, only the one whose cost you can live with.
  3. "Are we sticky? When do we take it off?"
    Sticky sessions are a bridge, not a destination. If the answer to the second half is "we hadn't thought about it", the crutch has quietly become the design, and a deploy still logs everyone out.
  4. "What does our health check actually test?"
    If it only proves the process is up, it will keep a broken server taking traffic. If it fails on every shared-dependency blip, one blip takes the whole fleet down. It should test what this server needs to do its own job — no less, no more.
  5. "Can we lose a server right now without anyone noticing?"
    The definition of stateless, phrased as a dare. If the honest answer is yes, autoscaling, rolling deploys and surviving a crash all come for free. If it is no, find the note that only one server is keeping.

Tiếng ViệtBạn không cần thuộc kỹ thuật nào. Chỉ cần một câu hỏi cho mọi state giữa các request — "request sau rơi sang server khác có còn chạy không?" — biết session đang ở đâu và cái giá của nơi đó, và trả lời được câu: mất một server ngay bây giờ có ai nhận ra không.
