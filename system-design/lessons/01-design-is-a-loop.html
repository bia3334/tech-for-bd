What one request costs · Lesson 01

Design is a loop, not a diagram

Somebody says "design a URL shortener" and hands you a marker. What they are asking for is not a picture. It is five moves, made in order, each one allowed to send you back to the one before — and the picture is only what the moves leave on the board.

01Ground floor

The question is not the one it sounds like

TAPAny word with a dotted underline opens a plain explanation in English and Vietnamese, plus where that thing shows up once a system is actually running. Nothing here assumes you have met it before.

Here is what usually happens. The marker is barely in your hand and there is already a box labelled API, an arrow to a box labelled DB, and — because everyone has seen the diagram before — a third box labelled Cache and a fourth labelled Load balancer. Four boxes in forty seconds. It looks like progress. It is the opposite: you have drawn the answer to a question nobody asked yet.

Because "design a URL shortener" is not one question. Shortening links for a team of twelve and shortening links for a social network are different products that happen to share a name. One of them is a weekend with a single database. The other has a redirect path that answers a hundred thousand times a second and a key generator that must never hand out the same key twice. You cannot know which one you are designing until you ask — and the asking is the first move, not a formality before the real work.

So a design session is a loop. You ask what the system must do and how well; you turn the answers into a few numbers; the numbers tell you which boxes are earned and which are decoration; you go one level deeper on the single box that is genuinely hard; and you say out loud what you gave up. Then, very often, the deep dive changes a number, and you go round again.

1 · Requirements — what, and how well
Shorten, redirect, list my links. Then the numbers: how many users, how fast a redirect, how long a link lives, how many nines.

The loop is the same in an interview, in a design document, and in the meeting where somebody asks whether the thing will hold up on launch day. The setting changes the amount of time you have. It never changes the moves.

In productionThe loop leaves fingerprints. A design doc has a requirements section with numbers in it, a capacity paragraph, a diagram, one component with its own deep section, and a heading called "Alternatives considered". When one of those is missing, the system usually reveals which one during its first incident.

02The idea

Five moves, run once on a URL shortener

Move one — requirements. There are two kinds and they are worth keeping apart. A is a verb the product does: take a long URL and return a short one; redirect anyone who opens the short one; let a user see the links they made. Three verbs. Everything else — custom aliases, expiry dates, click statistics — you ask about explicitly, because each one you accept adds a box later. A is how well, and it has to carry a number: a redirect in under 100 milliseconds at the 99th percentile; 99.9% of the time; links kept for five years. "It should be fast" is not a requirement. It is a hope.

Move two — estimate. Say a million people use it daily and one in ten makes a link. That is 100,000 new links a day, which over 86,400 seconds is barely more than one write a second. If each link is opened a hundred times, that is about 116 reads a second on average — call it 350 at peak. Five years of links at 500 bytes each is under 100 gigabytes. The took a minute and it has already told you the most important thing about this system: at this size there is no hard part. One application server and one database will do it, and anybody who draws more is drawing for a different product.

Now change one input. A hundred million daily users. Writes go to about 116 a second — still easy. Reads go to eleven thousand a second, thirty-five thousand at peak. That is a number one database should not be asked to answer on its own, and it is the number that earns the cache. Notice the order: the box appeared because the arithmetic said so, not because the diagram looked lonely without it. The did the deciding.

Move three — sketch. Client, load balancer, a row of stateless application servers, a cache in front of a database. For the big version, a separate service that hands out unique keys, so that generating a key and checking it is unused never happens inside the write. Six boxes. Each one can name the number that put it there — which is exactly the test of a good .

A box with no number behind it is not architecture. It is a guess wearing a rectangle.

Move four — deep dive. Pick the one thing that is hard and go one level down. For the big shortener that is the redirect path: what exactly is in the cache, what happens on a miss, what the p99 looks like when the cache node restarts and every request falls through at once. Or it is the key generator: how does it never repeat, what happens when two servers ask for a key in the same microsecond, what if the service is down. You do not deep-dive everything. You deep-dive the , because the bottleneck is the only place where getting it wrong changes what the user feels.

Move five — trade-offs. This is where most sessions end early, and it is the move that separates a design from a drawing. The cache made redirects fast — and it means a link somebody just deleted keeps resolving until its entry expires. Pre-generating keys took the collision check off the write path — and it added a service that can itself run dry or fall over. Say each one in a sentence. A nobody said out loud is a surprise waiting for a production incident to introduce itself.

In productionThe two kinds of requirement live in two different places once the system is real: the functional ones are the endpoints in the router, the non-functional ones are the SLO dashboard and the alert thresholds. If one of the numbers from move one is not on a dashboard, the system is not meeting it, whatever the doc says.

03The danger

Three ways the loop gets skipped, and what each one costs

Nobody skips the loop on purpose. It gets skipped because each move feels optional in the moment, and each skip has a specific bill that arrives later.

Boxes before questions

The forty-second diagram. Its cost is not that it is wrong — it may even be right — it is that you cannot tell. Without requirements, there is no test a diagram can fail, so the conversation drifts into taste: "I'd put Redis there." "I'd use Kafka." Nobody can win an argument about a system nobody has described. In an interview this reads as someone who has memorised diagrams; in a team it reads as someone who has already decided.

An estimate you did not do

Skip the arithmetic and every box becomes equally important, which means the deep dive lands on whichever part you happen to know best rather than the part that will break. The tell is a design that spends ten minutes on the database schema of a system whose database will be idle, and one sentence on the redirect path that carries 99% of the traffic. The estimate is what tells you where to spend your attention. Without it you spend it evenly, which is to say badly.

A trade-off you never said

Every choice in a design costs something, and the cost does not go away because it was not mentioned. A cache that nobody said could serve stale data is still serving stale data; the only difference is that the first person to find out is a user. The habit to build is mechanical: each time you add a box, finish the sentence "…and the price of that is". If you cannot finish it, you do not yet understand the box.

The line you never cross

Never draw a box you cannot attach a number to.

A cache is earned by a read rate or a latency target. A queue is earned by work that must not block a user. A second database is earned by bytes or by writes per second. If the number that earns a box does not exist yet, leave the box off and write down the number at which you would add it. That sentence — "at ten thousand reads a second we add a cache" — is worth more than the box, because it is the box and the reason, and the reason is what the next engineer needs.

Where the loop shows up

Four rooms, one set of moves. The time available changes; the order does not.

  • The interview — 45 minutesFive minutes of questions, three of arithmetic, ten on the sketch, fifteen on one deep dive, the rest on trade-offs and what you would do at ten times the load. Interviewers score the moves, not the picture.
  • The design document — a weekThe same five headings. Requirements with numbers, capacity, diagram, one component in depth, alternatives considered. Reviewers who cannot find a heading assume the move was skipped, because it usually was.
  • The estimate meeting — an hour"Will this hold on launch day?" is move two asked by somebody who does not call it that. Answer with the arithmetic, and with which box is closest to its limit.
  • The incident review — the morning afterEvery postmortem is the loop run backwards: which number was wrong, which box was missing, which trade-off was never said. Running it forwards is cheaper.

In productionThe unsaid trade-off is the most common root cause in postmortems that nobody writes down as a root cause. The report says "cache served stale data". The truth is "we added a cache without finishing the sentence".

    07Take away

    Five questions worth asking

    1. "Before I draw anything — how many users, and how fast does a redirect have to be?"
      Say it in the first thirty seconds, every time. It signals that you know a shortener for twelve people and one for a hundred million are different products, and it buys you the numbers everything else depends on.
    2. "Which number put this box here?"
      Ask it of your own diagram before anyone else does. A box that can answer is architecture. A box that cannot is a guess, and the honest move is to erase it and write down the number at which it would come back.
    3. "Reads or writes — which one is the system actually made of?"
      The read/write ratio decides whether you optimise the path that stores or the path that serves. A shortener is a hundred to one for reads; a logging pipeline is the reverse. Get this wrong and every later decision optimises the quiet half.
    4. "Which one part is hard? Let's spend the time there."
      The estimate points at it. Spending equal time on every box is the most common way to run out of time before reaching the part that will break, and reviewers notice the sentence about the redirect path far more than the paragraph about the schema.
    5. "…and the price of that is?"
      Finish the sentence for every box you add. If you cannot, you do not yet understand the box. If you can, you have just written the line the next engineer will need most.
